SECTION 2 — SIGNAL QUALITY ASSESSMENT
════════════════════════════════════════════════════════════════

Before extracting anything, classify the JD into one of these:

  high          JD has clear Required/Preferred sections with specific named stacks
  medium        JD has some specific stacks but structure is loose or incomplete
  low           JD has no specific stacks; only generic competency or role language
  laundry_list  JD lists 8 or more stacks across domains at roughly equal weight

Rules by signal quality:

  high / medium
    → Extract normally per rules in Section 3

  low
    → Infer the single most likely domain from job title, company name, and industry
    → Pick any 1 stack from that domain
    → Leave K2 minimal
    → Extract competency_signals (see Section 3)

  laundry_list
    → Apply the OR handling rule across all domains:
       pick any 2 stacks per domain from those listed
    → Do not attempt to rank or prioritize them


════════════════════════════════════════════════════════════════
SECTION 3 — EXTRACTION RULES
════════════════════════════════════════════════════════════════

── DOMAIN BREAKDOWN ────────────────────────────────────────────
  Estimate the % weight of each domain based on how central it is to the role.
  Must sum to 100.
  Omit domains with less than 5% weight.
  The domain with the highest % is the primary_domain.

── K1 HARD ─────────────────────────────────────────────────────
  Definition: skills whose absence would immediately disqualify a candidate.

  Rules:
  - Values must come EXACTLY from the approved stack list in Section 1
  - If a required skill is not on the list, place it in K2 instead — never K1 hard
  - Weight the Required / Must Have section of the JD heavily over Preferred
  - If a stack appears in both Required and Preferred sections, treat it as K1 hard
  - If a stack appears only in Preferred or Nice to Have, place it in K2 only
  - Primary domain (highest %): max 3 stacks
  - All other domains: max 2 stacks
  - Within each domain, list stacks in order of importance (most critical first)
  - If framework is explicitly named (e.g., Django), use that key (python_django)
    If only the language is named (e.g., Python), use the generic key (python)

── OR HANDLING ─────────────────────────────────────────────────
  Trigger: JD uses OR / slash / comma-separated equivalents for stacks
  Examples: "React, Vue, or Angular" | "Python/Java/Go" | "AWS or GCP"

  Rule:
  - Pick any 2 from the listed options
  - If the OR group is in a Required section → place chosen 2 in K1 hard
  - If the OR group is in a Preferred section or context is ambiguous →
    place ALL options as a grouped array in K2 (do not pick for K1)

  Example K2 group output: ["React", "Vue", "Angular"]
  This signals: any one of these satisfies the requirement.

── K1 SOFT ─────────────────────────────────────────────────────
  Definition: non-technical gate requirements.
  Examples: "5+ years experience" | "Bachelor's degree required" | "led a team of 5+"

  Rules:
  - Max 3
  - Only include if explicitly stated as required in the JD
  - Do NOT include vague nice-to-have phrases or soft leadership mentions
  - Do NOT include security clearance here (handled separately)

── K2 ──────────────────────────────────────────────────────────
  Definition: contextual keywords a strong candidate is expected to have,
  even if not a hard gate.

  Rules:
  - Include technologies, patterns, protocols, and tools not on the approved list
  - PROTOCOLS always go here, never in K1:
    REST API, GraphQL, gRPC, WebSocket, OAuth, JWT, etc.
  - ARCHITECTURE PATTERNS always go here, never in K1:
    microservices, event-driven, serverless, MVC, etc.
  - For OR groups from Preferred sections, group as an array:
    ["AWS", "GCP", "Azure"] = any one suffices
  - Do NOT duplicate K1 hard values in K2

── K3 (TRULY DROPPED) ──────────────────────────────────────────
  Definition: keywords read and consciously thrown away. Not useful for
  tailoring, injection, or tone. Audit trail only.
  K3 is never used anywhere in the tailoring pipeline.

  Only include:
  - Leftover OR list items not selected as the 2 picks
    e.g. OR list was [Go, Python, Ruby, Rust, Java], picked Go + Python
    → K3 gets ["Ruby", "Rust", "Java"]
  - Very niche or rarely-seen tools appearing in under 5% of similar
    JDs: e.g. Ada, Wagtail CMS, COBOL, LabVIEW
  - Company-internal framework names meaningless outside that org:
    e.g. "PNC Enterprise Risk Framework", "WBD ADD process"
  - Extremely vague filler with zero specificity:
    e.g. "innovative solutions", "fast-paced environment", "team player"

  Do NOT put in K3 — these belong in K2:
  - "agile / scrum"             → common process signal
  - "code reviews"              → common engineering practice
  - "REST API", "GraphQL"       → always K2 (protocol rule)
  - "microservices"             → always K2 (architecture rule)
  - "Docker", "Git"             → common tools, include if mentioned
  - "cross-functional collaboration", "stakeholder management",
    "technical mentorship"      → K2 or competency_signals

  Never include:
  - Items already in K1 or K2
  - Benefits, compensation, legal, or HR boilerplate
  - Things never evaluated

  Format: flat array of plain strings only, no groups or nested arrays.

── COMPETENCY SIGNALS ──────────────────────────────────────────
  Definition: generic role emphasis signals extracted when the JD lacks
  specific stack information. Used to guide bullet tone, not stack selection.

  Populate this field only when:
  - signal_quality is "low", OR
  - The JD contains generic competency language alongside or instead of stacks
    (e.g., "SDLC, Technical Troubleshooting, Architecture, Customer Solutions")

  For each signal found, classify into one of these categories:
    architecture    → System design, application architecture, scalability
    leadership      → Team lead, mentoring, tech lead, cross-functional ownership
    process         → SDLC, release management, CI/CD process, agile/scrum
    user_impact     → Customer solutions, UX, end-user focus, product thinking
    testing         → QA, test planning, application testing, quality assurance
    documentation   → Technical writing, documentation, specs

  Max 4 signals. Leave as empty array [] for high or medium signal JDs.

── SECURITY CLEARANCE ──────────────────────────────────────────
  clearance_required: true if any security clearance is explicitly required
                      or preferred anywhere in the JD, otherwise false
  clearance_level:
    "active"             → must currently hold clearance
    "ability_to_obtain"  → must be eligible / willing to pursue clearance
    "not_required"       → no clearance mentioned

════════════════════════════════════════════════════════════════
SECTION 5 — EDGE CASES
════════════════════════════════════════════════════════════════

  - JD is empty or under 20 meaningful words:
    → signal_quality: "low", all other fields empty / default values

  - No domain exceeds 5% confidently:
    → Set primary_domain to what the job title most strongly implies

  - A stack appears in both Required and Preferred sections:
    → Treat as K1 hard

  - A stack appears only in Preferred or Nice to Have:
    → K2 only, never K1

  - Required skill exists but is not on the approved stack list:
    → Place in K2 as a plain string, not K1 hard

  - Clearance mentioned only as preferred (not required):
    → clearance_required: true, clearance_level: "ability_to_obtain"
